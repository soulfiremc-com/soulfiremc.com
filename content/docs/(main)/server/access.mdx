## Generate an API token

Run this command in the SoulFire server console:

```text
generate-token api
```

The token works as the API key for the SoulFire API, MCP, and SDK clients.
It uses the permissions of the current SoulFire user.
For a remote client, enter the backend URL and that token.
Check the identity with `whoami` in the authenticated terminal.

The API and WebDAV use separate token audiences.
A token from `generate-token webdav` is not an API token.

## Revoke a token

A new token does not revoke older tokens.
To revoke a leaked token, invalidate the user's sessions.
This ends every API token issued to that user before that moment.

- A user invalidates their own sessions with `ClientService.InvalidateSelfSessions`.
- An administrator invalidates another user's sessions with `UserService.InvalidateSessions`.

Then generate a new token for each client that still needs access.

## Use HTTPS for remote clients

Terminate HTTPS at a reverse proxy or tunnel in front of SoulFire.
Use the [automated setup](/docs/server/automated-setup) or the HTTPS examples in [Docker deployment](/docs/server/docker).
The configured hostname must match the certificate presented to the client.

For a local connection, the default backend port is `38765`.
A dedicated server listens on all network interfaces (`0.0.0.0`) over plain HTTP by default.
Set `-Dsf.grpc.host=127.0.0.1` when remote access is unnecessary, or when a reverse proxy on the same host provides HTTPS.
The [Java guide](/docs/server/java) describes `sf.grpc.host` and `sf.grpc.port`.

## Grant project access

Use the client's user management and project permission controls for the user who needs access.
Grant only the projects and actions required for that workflow.
Server-wide administration and project access are separate permissions.

Sign in as that user after the change.
Check that the intended project appears and its required actions work.
Also check that unrelated projects remain inaccessible.

For programmatic management, use the [administration guide](/docs/sdk/administration) and the generated [UserService and InstanceService contracts](/docs/openapi).

## Diagnose an authorization problem

- An unauthenticated request points to a missing, expired, invalid, or wrong-audience token.
- A denied action with a valid login points to the user's permissions.
- A successful API login does not grant Minecraft permissions to the bot.

Check backend logs and the full error before creating another token.
Use [account and authentication troubleshooting](/docs/troubleshooting/accounts-and-authentication) to distinguish API access from Minecraft login.
