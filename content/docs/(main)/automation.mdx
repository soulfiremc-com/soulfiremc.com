SoulFire provides several automation layers. Choose the narrowest one that
owns the decision you need.

| Goal | Use |
| --- | --- |
| Run one operator action | [Commands](/docs/reference/commands) |
| React to chat, timers, or events in the GUI | [Visual scripting](/docs/scripting) |
| Keep a reusable action near the game loop | [Durable tasks](/docs/sdk/tasks) |
| Build an application from observations and actions | [Official SDK](/docs/sdk) |
| Run first-party progression policy | [Beat-game runner](/docs/sdk/automation) |
| Add server-owned domain capabilities | [Plugins](/docs/sdk/plugins) |

## SoulFire is the remote client

SoulFire owns Minecraft protocol state, pathfinding, direct inputs, control
arbitration, and reusable tasks. Applications own their goals and decide how
to combine those capabilities.

The first-party beat-game planner therefore runs in
`@soulfiremc/beat-game`, not inside the SoulFire server or SoulFireClient. The
TypeScript worker can restart from checkpoints, coordinate a team, call
plugin-defined RPCs, and replace policy steps without changing SoulFire core.

<Callout type="info">
  SoulFireClient does not contain a native beat-game dashboard. Run and
  observe the application from your TypeScript worker, logs, or your own
  operator interface.
</Callout>

## Reusable tasks versus policy

A collect-blocks task is reusable. It stays close to the game loop and can
continue according to its disconnect policy. Deciding that a team needs eight
logs before entering the Nether is game policy and belongs in the worker.

The same distinction applies to plugins. A plugin can intentionally expose a
typed server-side capability. The application still decides when that
capability serves its plan.
