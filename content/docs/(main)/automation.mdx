SoulFire provides several automation options.
Choose the simplest option that can do your task.

| Goal | Use |
| --- | --- |
| Run one operator action | [Commands](/docs/reference/commands) |
| React to chat, timers, or events in the GUI | [Visual scripting](/docs/scripting) |
| Keep a reusable action near the game loop | [Durable tasks](/docs/sdk/tasks) |
| Build an application from observations and actions | [Official SDK](/docs/sdk) |
| Run first-party progression policy | [Beat-game runner](/docs/sdk/automation) |
| Add server-owned domain capabilities | [Plugins](/docs/sdk/plugins) |

## SoulFire is the remote client

SoulFire manages the Minecraft protocol, pathfinding, direct input, control,
and reusable tasks. Applications set goals and combine these features.

The beat-game planner runs in `@soulfiremc/beat-game`.
It does not run inside the SoulFire server or SoulFireClient.
The TypeScript worker can resume checkpoints, coordinate teams, and call plugin RPCs.
You can change its plan without changing SoulFire.

<Callout type="info">
  SoulFireClient does not contain a native beat-game dashboard. Run and
  observe the application from your TypeScript worker, logs, or your own
  operator interface.
</Callout>

## Reusable tasks versus policy

A collect-blocks task is reusable.
It runs near the game loop and follows its disconnect policy.
The worker decides whether a team needs eight logs before entering the Nether.

The same rule applies to plugins.
A plugin can expose a typed server feature.
The application decides when to use that feature.
