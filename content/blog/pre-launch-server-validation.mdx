## What to check before launch

Launch day brings your largest wave of new players, and a laggy or broken first visit gives them a reason not to return. Work through the phases below in order. The most important single test is the [launch surge load test](#phase-5-load-testing-2-3-days-out): connect at least twice your expected peak in bots to a copy of your server, and watch TPS, errors, and join failures.

## Pre-Launch Validation

<Steps>
  <Step>
    ### Phase 1: Infrastructure (2-4 Weeks Out)

    Start with the foundation. Plugin tuning cannot fix slow hardware or missing backups. The load test in phase 5 tells you whether your hardware is enough, so leave time to upgrade after it.

    Run baseline checks on your hardware first:

    ```bash
    # Disk I/O speed: target >200 MB/s for SSD (run in the server directory)
    dd if=/dev/zero of=./ddtest bs=1G count=1 oflag=direct && rm ./ddtest

    # Network bandwidth (needs an iperf3 server that you control)
    iperf3 -c iperf.example.com

    # Disk space: keep >50% free for headroom
    df -h
    ```

    Red flags include HDD storage and shared hosting where other customers can use up the CPU.

    Test your backups before your first crash. Create a full backup, extract it to a separate directory, and confirm the world loads cleanly. Then schedule automated backups via cron: every 6 hours locally and daily offsite.

    On security: lock down your firewall to only the ports you need (25565, 22, 80/443 if applicable). Disable SSH password authentication, install Fail2ban, and keep the backend IP hidden behind a proxy if you can.
  </Step>

  <Step>
    ### Phase 2: Server Configuration (1-2 Weeks Out)

    <Callout type="info" title="Detailed Optimization Guide">
    For a thorough walkthrough of view/simulation distance tuning, entity limit configuration, chunk pregeneration, JVM flags, and profiling with Spark, see our [Stress Testing Minecraft Servers](/blog/stress-testing-minecraft-servers) guide. The sections below cover what to verify, not how to tune from scratch.
    </Callout>

    Get your numbers on an empty server first using [Spark](https://spark.lucko.me/). You want TPS at 20.0, MSPT under 10ms, RAM under 25% of max, and CPU under 20%. That's your baseline.

    **Configuration checklist:**

    - **View and simulation distance:** Lower simulation distance reduces entity processing overhead without sacrificing player visibility. See the [stress testing guide](/blog/stress-testing-minecraft-servers#view-and-simulation-distance) for recommended values by server size.
    - **Entity limits:** Tighten Paper's mob spawn caps and collision limits if your profile shows entities as a large cost.
    - **World pregeneration:** Without it, many players exploring on launch day force chunk generation and can drop TPS far below 20. Use [Chunky](https://github.com/pop4959/Chunky) to pregenerate at least a 5,000-block radius from spawn. This can take hours, so plan accordingly.
    - **JVM flags:** On Java 25+ with 8+ cores, use [ZGC with Compact Object Headers](/blog/stress-testing-minecraft-servers#java-flags) for short GC pauses. On older Java or smaller hardware, use [Aikar's G1GC flags](https://docs.papermc.io/paper/aikars-flags). Match Xms and Xmx to your available RAM.
    - **Server software:** [Paper](https://papermc.io/) is the baseline. For 100+ player targets, consider [Pufferfish](https://pufferfish.host/).

    Check each setting, restart, and make sure your numbers haven't gotten worse before moving on.
  </Step>

  <Step>
    ### Phase 3: Plugin Validation (1 Week Out)

    Start the server and watch the logs for errors:

    ```bash
    tail -f logs/latest.log | grep -i error
    ```

    Common sources of trouble include multiple economy plugins conflicting, duplicate feature plugins (two claim systems), and version mismatches. For each critical plugin, including economy, permissions, claims, chat, teleportation, and anti-cheat, confirm it loads cleanly, test its primary features, test its interactions with other plugins, and check that permissions are correctly assigned.

    Walk through each rank (default, member, VIP, moderator, admin) and make sure players can use exactly the commands they should, and nothing more. Check chat prefixes, tab list formatting, and look for permission leaks that give default players access to moderation commands.
  </Step>

  <Step>
    ### Phase 4: Player Experience (3-5 Days Out)

    Join your own server like you've never seen it before. Read the welcome message. Follow the instructions. Complete the starter tasks. The whole thing should take 10-20 minutes and leave a new player with basic tools, a sense of direction, and a reason to keep playing.

    At spawn, look for dark patches in the lighting, unfinished builds (leftover scaffolding is classic), unreadable signs, hazards near the spawn point, and a `/help` command that tells players something useful. Post your rules where people can find them.

    Then walk through the progression path and time it: first purchase, iron tools, diamond tools. Compare each earning method. If one pays far more than the others, players will find it in the first days and prices will inflate.
  </Step>

  <Step>
    ### Phase 5: Load Testing (2-3 Days Out)

    Five friends cannot show you how the server behaves with 100 players. You need bots. The [stress testing guide](/blog/stress-testing-minecraft-servers) covers the full method: staged load, realistic bot behavior, spike tests, and endurance runs. Run the test on a copy of your server, and focus on these launch scenarios:

    - **Mass join:** Simulate 50-100 players connecting within a few minutes. This is the launch surge. Keep an eye on connection failures, spawn area performance, and TPS dips during the initial flood.
    - **Spawn pressure:** Your spawn area will bear the heaviest load on day one. Test it at your full target player count and look for rubber-banding or block interaction delays.
    - **Endurance:** Run at 50-75% of target capacity for 4-12 hours. Monitor for memory leaks, TPS degradation over time, increasing GC pauses, and accumulating errors in the log.

    With [SoulFire](/download), a launch simulation looks like this: 100 bots that join over 10 minutes (a join delay of about 6 seconds), with **Anti AFK** turned on. **Auto respawn** and **Auto reconnect** are on by default. Let it run for 2 hours while you watch Spark and the console. If an anti-bot plugin or the server's connection throttle rejects the bots, allow your test IP on the test copy only, and keep the real limits for launch. The [SoulFire testing guide](/docs/testing) shows how to prepare the run, add load in stages, and record the results.

    **Your server is ready when:**

    - 95 or more of 100 bots connect
    - TPS stays above 18 during the surge and above 19 once joins stop
    - The console shows no new errors or exceptions
    - Spawn handles the full bot count without rubber-banding
    - Commands stay responsive

    If fewer than 85 bots connect, TPS drops below 15, or memory use passes 90%, fix the configuration, plugin errors, or hardware before launch. Test with 100 bots before you advertise for 50 players.

    Also test latency from the regions where your players live. Under 100ms is good, and 100-200ms is acceptable.
  </Step>

  <Step>
    ### Phase 6: Staff and Communications (1-2 Days Out)

    Your staff need to know what to do when something breaks. Write up a quick-reference doc with the three or four most common issues: "can't claim land" (check their balance), "can't use command" (check their rank), "grief reported" (use `/co inspect`, rollback if needed). Make sure everyone has tested these commands on the actual server, not just read about them. Set up an on-call schedule so you have coverage during peak hours.

    On Discord: have your announcement drafted, your channel permissions locked down so launch-day chaos doesn't spill everywhere, and at least one staff bot responding to commands.
  </Step>

  <Step>
    ### Phase 7: Final Validation (Day Before Launch)

    Do a complete walkthrough of the player journey: join, orientation, resource gathering, claiming, building, social features, and economy. If something breaks during this walkthrough, fix it now, not tomorrow with 100 players online.

    Run final system health checks:

    ```bash
    # Verify services
    ps aux | grep java
    ps aux | grep mysql

    # Disk space
    df -h

    # DNS resolution
    nslookup your-server.com

    # Recent backup exists
    ls -lh backups/

    # No errors in logs
    tail -100 logs/latest.log
    ```
  </Step>
</Steps>

## Launch Day Protocol

<Callout type="warning" title="Launch Day Priorities">
- **Stability over features:** disable anything that isn't rock-solid
- **Have a rollback plan:** be ready to revert if critical issues emerge
- **Announce delays right away**
- **All staff online:** no exceptions during the launch window
</Callout>

One hour out, restart the server fresh. Clear temporary files. Confirm TPS is at 20.0, all plugins loaded green, and external connections work. Get staff assembled and comms open.

When you flip the switch, whether that means removing the whitelist or starting to add players, send your announcement and start monitoring. Watch player count, TPS, chat, and console errors. Staff should be actively welcoming players and answering questions, not lurking in a staff channel.

In the first hour, fix anything that blocks core gameplay right away: broken claims, connection issues, economy bugs. Cosmetic problems such as sign typos can wait until tomorrow.

## Post-Launch

For the first 24 hours, track the numbers that matter: peak concurrent players, total unique joins, average session length, minimum TPS during peak, crashes, and plugin errors.

During the first week, review what happened. Which plugins threw errors? Where did players get stuck or confused? Did the economy hold up or did someone find an exploit on day two? Fix what you find, and run the bot load test again before your next large update.
